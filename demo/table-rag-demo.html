03生成 SQL通过校验
SELECT SUM(o.pay_amount)               AS gmv,
       COUNT(DISTINCT o.order_id)      AS orders
FROM dy_order o
JOIN dy_product p ON o.product_id = p.product_id
WHERE p.category_name = '益生元'
  AND o.pay_time >= '2026-09-01'
  AND o.pay_time <  '2026-10-01'
  AND o.order_status IN ('已支付','已完成');
时间用左闭右开（>= 09-01 AND < 10-01），不用 BETWEEN——否则最后一天 23:59 之后的单子会漏掉。

02字段匹配有歧义
候选字段相似度字典里的注释

uv 和 pv 只差 0.07。口语里"访客数""浏览量"经常混着说，这是整条链路的第一个不确定点。选错不会报错，只会给你一个看起来正常的错数字。
03生成 SQL语法正确
SELECT t.stat_date,
       SUM(t.uv)  AS visitors
FROM dy_traffic t
JOIN dy_product p ON t.product_id = p.product_id
WHERE p.category_name = '少女丹'
  AND t.stat_date >= '2026-10-19'
  AND t.stat_date <= '2026-10-25'
GROUP BY t.stat_date
ORDER BY t.stat_date;
语法、表名、连接条件、时间范围全部正确。校验器全部通过——但校验通过不等于结果对。

05归因卡在元数据层
先排除什么 SQL 语法没问题、字段选对了、时间范围没错 —— 所以不是生成层的问题。别去改 prompt。 真正的原因 category_name 的实际取值里没有"少女丹"。 怎么确认 跑一条
SELECT DISTINCT category_name FROM dy_product WHERE category_name LIKE '%少女%'
返回 少女丹·私护凝胶 —— 库里存的是完整品名，不是简称。 怎么修（按性价比排序）
  1. 建一张取值映射表，把简称、别名、错别字映射到真实取值
  2. 枚举型字段在生成 SQL 前先查一次 distinct 值，做模糊匹配再拼条件
  3. 空结果时自动回查一次，把"没查到"和"值为 0"区分开
这条要记住 这是数据字典和真实数据脱节，属于元数据层。同一类问题在"退款率""新客数"上会以口径分歧的形式反复出现——它们都不是模型能力问题。
